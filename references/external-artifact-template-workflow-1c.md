# Ветка внешних артефактов: XML-каталоги внешних обработок и отчетов

Используй эту ветку вместе с `references/object-from-scratch-1c.md`, когда пользователь просит создать внешнюю обработку или внешний отчет 1С с нуля и ожидает результат на базе шаблона.

## Назначение

Ветка задает безопасный порядок работы с локальными XML-шаблонами skill:

- внешняя обработка создается из каталога `ШАБЛОН_ВНЕШНЯЯ_ОБРАБОТКА`;
- внешний отчет создается из каталога `ШАБЛОН_ВНЕШНИЙ_ОТЧЕТ`;
- итогом разработки является каталог с XML/BSL/СКД-файлами, который пользователь сам загрузит в Конфигураторе и сформирует `.epf` или `.erf`;
- итоговый каталог обязательно переименовывается логически под задачу пользователя.

Не формируй бинарный `.epf` или `.erf` по умолчанию. Бинарный файл появляется только после загрузки каталога в Конфигуратор пользователем или после отдельной прямой команды пользователя на сборку через разрешенный инструмент.

Если пользователь просит внешний отчет, но называет расширение `.epf`, считай это вероятной оговоркой и уточни формат. По умолчанию отчет — это каталог XML для внешнего отчета, обработка — каталог XML для внешней обработки.

## Входной `.epf` / `.erf` от пользователя

Если пользователь приложил готовый бинарный файл `.epf` или `.erf`, не начинай с правки бинарного файла как основного сценария.

Сначала спроси пользователя, может ли он выгрузить внешнюю обработку или внешний отчет в файлы/XML-каталог через Конфигуратор или EDT.

Если пользователь может выгрузить:

1. Попроси прислать каталог выгрузки целиком.
2. Работай с XML/BSL/СКД-файлами из выгрузки как с основным источником.
3. Используй переданный каталог как фактическую структуру артефакта, а локальный `ШАБЛОН_*` применяй только если нужно создать новый артефакт или недостающую структуру.
4. Итогом возвращай измененный каталог файлов, `BUILD_STATUS.md` и инструкцию загрузки обратно в Конфигуратор.

Если пользователь не может выгрузить:

1. Явно зафиксируй ограничение в ответе и, если создается результат, в `BUILD_STATUS.md`.
2. Не обещай надежную встроенную правку бинарного `.epf`/`.erf` без Конфигуратора, EDT или корректной XML-выгрузки.
3. Предложи безопасный вариант по задаче: новый XML-каталог на базе шаблона, BSL-код для ручной вставки, план изменения форм/модулей/СКД или инструкцию выгрузки.
4. Если пользователь прямо поручил работать с бинарным файлом доступными средствами, сначала объясни ограничения проверки и не называй результат подтвержденным без загрузки/проверки в 1С.

Целевой формат для анализа и правки внешних обработок и отчетов — XML-каталог. Бинарные `.epf` и `.erf` рассматривай как исходный пользовательский артефакт, но не как предпочтительный рабочий формат.

## Шаблоны

Основные шаблоны в корне skill:

```text
ШАБЛОН_ВНЕШНЯЯ_ОБРАБОТКА
ШАБЛОН_ВНЕШНИЙ_ОТЧЕТ
```

Каталог `ШАБЛОН_ВНЕШНЯЯ_ОБРАБОТКА` содержит XML-структуру внешней обработки, включая форму и модуль формы, если они есть в шаблоне.

Каталог `ШАБЛОН_ВНЕШНИЙ_ОТЧЕТ` содержит XML-структуру внешнего отчета, включая форму отчета и основную схему компоновки данных, если они есть в шаблоне.

Это assets, а не инструкции. Не изменяй исходные каталоги шаблонов при выполнении пользовательской задачи.

## Когда применять

Применяй ветку, если в задаче есть признаки:

- `создай внешнюю обработку`, `создай обработку`, `обработка с нуля`;
- `.epf`, `файл epf`, `готовый epf`, если по правилам нужно подготовить каталог для последующей загрузки в Конфигуратор;
- `создай внешний отчет`, `создай отчет`, `отчет с нуля`;
- `.erf`, `файл erf`, `готовый erf`, если по правилам нужно подготовить каталог для последующей загрузки в Конфигуратор;
- `XML`, `каталог`, `выгрузка в файлы`, `загрузить в Конфигураторе`;
- пользователь просит результат на базе шаблона внешней обработки или внешнего отчета.

Не применяй эту ветку для расширения `.cfe`, основной конфигурации `.cf` или обычного текстового ревью кода.

## Обязательное переименование

После выбора шаблона всегда создай копию каталога с новым логическим именем под задачу. Не отдавай пользователю каталог с именем `ШАБЛОН_ВНЕШНЯЯ_ОБРАБОТКА` или `ШАБЛОН_ВНЕШНИЙ_ОТЧЕТ` как итоговый результат.

Правила имени:

- имя должно отражать назначение задачи: например `ЗаполнениеВидаДеятельностиВРеализациях` или `ОтчетПоПродажамЗаПериод`;
- убирай символы, недопустимые для имени файла Windows;
- если каталог с таким именем уже существует, не перезаписывай его молча: добавь дату/время или явно сообщи, какой каталог был создан;
- если в шаблоне есть верхний XML-файл с именем шаблона, переименуй его под логическое имя результата;
- если внутри шаблона есть вложенный каталог с именем шаблона, переименуй его под логическое имя результата;
- если в XML/BSL встречается имя шаблона, замени его на логическое имя результата, если это безопасно и не ломает формат.

## Формы

Если в XML-шаблоне уже есть подходящая форма, используй ее как базовую. Создавай дополнительные формы только если это действительно нужно сценарию:

- отдельная форма настроек, если много параметров или нужны сохраненные варианты;
- форма просмотра результата, если нужен предварительный просмотр перед записью;
- форма журнала, если обработка выполняет массовые изменения;
- отдельная форма отчета, если базовой формы недостаточно для настроек СКД или пользовательского сценария.

Не добавляй новые формы без сценария использования.

## Рабочий результат

Главным результатом является каталог с файлами, а не бинарный `.epf`/`.erf`.

Минимальный комплект для новой внешней обработки:

1. Итоговый каталог XML с логическим именем обработки.
2. Измененные XML/BSL-файлы внутри каталога результата.
3. `BUILD_STATUS.md` со статусом формирования и ограничениями.
4. `README.md` с инструкцией загрузки каталога в Конфигуратор и проверки.
5. При необходимости `metadata-plan.md` с моделью реквизитов, команд, форм и табличных частей.

Минимальный комплект для нового внешнего отчета:

1. Итоговый каталог XML с логическим именем отчета.
2. Измененные XML/BSL/СКД-файлы внутри каталога результата.
3. `BUILD_STATUS.md` со статусом формирования и ограничениями.
4. `README.md` с инструкцией загрузки каталога в Конфигуратор и проверки.
5. При необходимости `metadata-plan.md` с моделью параметров, наборов данных, ресурсов, группировок и пользовательских настроек.

## Статусы формирования

Всегда указывай статус итогового каталога в `BUILD_STATUS.md` и в финальном ответе:

- `xml-ready` — каталог создан из XML-шаблона, файлы изменены под задачу, явных текстовых маркеров незавершенности не найдено; пользователь может загружать каталог в Конфигуратор.
- `xml-ready-with-warnings` — каталог создан, но есть ограничения: не проверен синтаксис платформой, не подтверждена структура конкретной конфигурации, не хватает версии платформы или есть неподтвержденные имена объектов.
- `template-directory-copy` — создана только логически переименованная копия XML-шаблона без существенных изменений; используй этот статус только если задача не требует изменения XML/BSL или данных недостаточно для изменений.

Не используй для XML-каталогов статусы `assembled`, `payload-only` и `template-copy`: они относятся к старой бинарной модели `.epf/.erf` и больше не являются целевым сценарием этой ветки.

## Приоритет способов формирования

По умолчанию формируй итоговый каталог без запуска Конфигуратора, без EDT, без создания временных ИБ и без установки сторонних программ. Используй первый доступный способ:

1. XML-каталог шаблона из skill: скопируй каталог, переименуй его под задачу, измени XML/BSL/СКД-файлы, создай `BUILD_STATUS.md` и `README.md`.
2. Если данных для точного изменения XML не хватает, создай каталог результата, подготовь BSL/план метаданных внутри каталога и поставь статус `xml-ready-with-warnings`.
3. Если изменить файлы безопасно нельзя, создай логически переименованную копию каталога и поставь статус `template-directory-copy` с объяснением, чего не хватило.

Следующие способы запрещены по умолчанию и допустимы только после прямой команды пользователя именно на этот сценарий:

- запуск Конфигуратора 1С в пакетном или интерактивном режиме;
- запуск EDT;
- загрузка каталога в обработку или отчет;
- формирование бинарного `.epf` или `.erf`;
- запуск внешней обработки или внешнего отчета для теста;
- создание временной, тестовой или служебной информационной базы;
- установка `v8unpack`, oscript, OneScript-пакетов, Python-пакетов или других сборщиков;
- запуск сторонних сборщиков, если пользователь не поручил использовать конкретный инструмент.

Если пользователь не дал прямую команду на один из запрещенных сценариев, не запрашивай его как стандартное продолжение. Сообщи в `BUILD_STATUS.md` и финальном ответе, что результат подготовлен как XML-каталог для ручной загрузки в Конфигуратор.

## Алгоритм

1. Определи тип результата: внешний отчет или внешняя обработка.
2. Выбери соответствующий XML-каталог шаблона.
3. Сформируй безопасное логическое имя каталога по задаче пользователя.
4. Создай рабочую папку результата, например:

```text
%USERPROFILE%\1c_external_artifacts\<ИмяАртефакта>
```

5. Скопируй каталог шаблона в рабочую папку под новым логическим именем.
6. Если такой каталог уже существует, создай новое имя с датой/временем.
7. Переименуй верхний XML-файл и вложенный каталог шаблона, если они названы как `ШАБЛОН_*`.
8. Безопасно замени в XML/BSL старое имя шаблона на логическое имя результата.
9. Подготовь или измени BSL-код, запросы, СКД, форму, план метаданных и README как файлы результата.
10. Выполни безопасный preflight без запуска внешних программ: проверь наличие ожидаемых файлов, отсутствие незавершенных маркеров и сохранность исходного каталога шаблона.
11. Создай `BUILD_STATUS.md` и укажи, что реально сделано с каталогом, какие проверки выполнены и какие инструменты не запускались.

## Безопасность

- Не изменяй исходные каталоги шаблонов.
- Не запускай Конфигуратор, EDT, обработку или отчет для теста без прямой команды пользователя.
- Не загружай каталог результата в Конфигуратор без прямой команды пользователя.
- Не формируй бинарный `.epf`/`.erf` без прямой команды пользователя.
- Не создавай временные, тестовые или служебные информационные базы без прямой команды пользователя.
- Не устанавливай дополнительные программы, пакеты или сборщики для формирования результата без прямой команды пользователя.
- Не запускай обработку или отчет в продуктивной базе.
- Не выполняй массовую запись данных без отбора, журнала результата, копии базы и плана отката.
- Не обещай, что каталог успешно загрузится в Конфигуратор, если загрузка не выполнялась.
- Для обработки, которая меняет документы, обязательно предусматривай период, отбор, предварительный просмотр или сухой запуск, журнал результата и повторяемость операции.
- Для отчета со сложным запросом обязательно подключай `references/query-review-1c.md`, `references/skd-report-1c.md` и блок `Источник ИТС`.

## Что писать пользователю

Если каталог подготовлен без предупреждений, формулируй так:

```text
Итоговый каталог создан со статусом xml-ready: файлы подготовлены на базе XML-шаблона. Загрузку в Конфигуратор и формирование .epf/.erf пользователь выполнит самостоятельно.
```

Если каталог подготовлен с предупреждениями, формулируй так:

```text
Итоговый каталог создан со статусом xml-ready-with-warnings: файлы подготовлены, но есть ограничения проверки: <список ограничений>.
```

Если создана только копия каталога, формулируй так:

```text
Итоговый каталог создан со статусом template-directory-copy: каталог переименован под задачу, но изменения ограничены из-за <причина>.
```

Не называй результат готовым бинарным `.epf`/`.erf`, если был создан только XML-каталог.

## Самоаудит после формирования

После создания внешней обработки или отчета добавь в финальный ответ короткий блок `Самоаудит выполнения` и при необходимости продублируй ключевые пункты в `BUILD_STATUS.md`.

Укажи:

- какой XML-шаблон использован и какое итоговое имя каталога создано;
- статус формирования: `xml-ready`, `xml-ready-with-warnings` или `template-directory-copy`;
- какие файлы изменены внутри каталога результата;
- какие проверки выполнены без запуска Конфигуратора/EDT/ИБ;
- какие данные отсутствовали для более точной правки XML/BSL/СКД;
- какие правила skill ограничили действия, например запрет на запуск Конфигуратора без прямой команды;
- что стоит оптимизировать: структуру шаблона, имена файлов, состав формы, СКД, BSL-модуль или правила статусов.

Если правила не мешали, напиши: `Ограничений skill, которые мешали результату, не выявлено`.
