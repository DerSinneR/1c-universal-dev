# Режим `интеграция`: обмены, API и внешние системы

Используй для HTTP-сервисов, REST-интерфейса, SOAP web-сервисов, планов обмена, регламентных и фоновых заданий, загрузок/выгрузок, очередей, повторной отправки, идемпотентности и интеграционных ошибок.

## Что определить в начале

- Направление обмена: входящий, исходящий, двусторонний.
- Транспорт: HTTP-сервис, REST, SOAP, файл, FTP/SFTP, почта, план обмена, внешняя компонента, COM, ручная загрузка.
- Формат: JSON, XML, XDTO, CSV, DBF, произвольный текст, двоичный файл.
- Инициатор и пользователь выполнения: интерактивный пользователь, регламентное задание, сервисный пользователь, внешняя система.
- Требования: синхронно или асинхронно, допустимые повторы, дедупликация, порядок сообщений, SLA.
- Контур: продуктив, тест, копия; есть ли журнал и план отката.

## Архитектура надежного обмена

- Входящий запрос сначала валидируй, затем нормализуй, затем записывай бизнес-данные.
- Для внешних сообщений храни внешний идентификатор и статус обработки, чтобы повторный вызов не создавал дубли.
- Не держи долгую транзакцию вокруг сетевого вызова.
- Для исходящих обменов отделяй подготовку данных от фактической отправки.
- Для массовых загрузок работай порциями, фиксируй прогресс и ошибки.
- Для регламентных заданий обеспечь повторный запуск без повторной порчи данных.

## HTTP, REST и web-сервисы

- Для HTTP-сервиса явно описывай URL-шаблон, HTTP-метод, параметры, тело запроса, код ответа и формат ошибки.
- Не возвращай технические исключения наружу без нормализации.
- Проверяй аутентификацию, права сервисного пользователя, RLS и разделение данных.
- REST-интерфейс может давать внешним системам широкие возможности чтения и изменения данных; не включай его без оценки модели доступа.
- SOAP/web-сервис применяй, если есть контракт и совместимость с потребителем важнее простоты HTTP.

## Планы обмена

- План обмена выбирай, когда нужно описать узлы обмена, состав данных и механизм обмена между информационными базами или внешними системами.
- Для каждого плана обмена фиксируй состав данных, правила регистрации изменений, порядок выгрузки и загрузки.
- Проверяй конфликты изменения одних и тех же данных в разных узлах.
- Не используй один универсальный обмен для сильно разных контуров, если состав данных и правила существенно различаются.

## Безопасность и журналирование

- Логируй внешний идентификатор, направление, время, статус, краткую ошибку и ссылку на объект 1С.
- Секреты, токены и пароли не храни в коде и не выводи в журнал.
- Для персональных данных и коммерческих данных проверяй минимальный состав передаваемых полей.
- Для продуктивного обмена нужен сценарий остановки, повторной обработки и ручного разбора ошибок.

## Формат ответа по интеграции

1. Тип интеграции и границы ответственности 1С.
2. Контракт: вход, выход, идентификаторы, статусы, ошибки.
3. Где хранить состояние обмена и как обеспечить идемпотентность.
4. Транзакции, права, RLS и сервисный пользователь.
5. Производительность и повторы.
6. Проверка: успешный обмен, дубль сообщения, ошибка внешней системы, таймаут, частичная загрузка, повторный запуск.
