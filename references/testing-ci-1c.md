# Режим `тесты`: качество, проверки и CI для 1С

Используй для планов проверки, релизного контроля, АПК, EDT, платформенной проверки конфигурации, BSL-проверок, регрессии, тестирования расширений, миграций и крупных доработок.

## Что определить в начале

- Что проверяется: основная конфигурация, расширение, внешняя обработка, отчет, EDT/XML-проект, релиз поставщика.
- Версия платформы и режим совместимости.
- Есть ли EDT, АПК, хранилище, Git, CI, тестовая база и копия продуктивных данных.
- Какой риск изменения: права, данные, проведение, обмен, отчетность, производительность, обновляемость.
- Что считается блокером релиза.

## Уровни проверки

### Быстрая локальная проверка

- Синтаксис модулей и директивы компиляции.
- Проверка клиент-серверного контекста.
- Проверка запросов и форм, затронутых изменением.
- Сценарий пользователя без полных прав.
- Для необязательного поиска простых BSL-паттернов можно вручную запустить `scripts/check-bsl.ps1 -Path <каталог-или-файл>`. Скрипт только читает файлы и выдаёт кандидаты на ревью; результаты не являются ошибками компиляции или подтверждением нарушения стандарта.

### Платформенная проверка конфигурации

Используй как обязательный минимум перед поставкой или крупным изменением, когда доступен конфигуратор. Она помогает выявлять логическую целостность, некорректные ссылки, синтаксический контроль модулей в разных режимах, неиспользуемые локальные процедуры и обработчики.

### АПК

Рассматривай АПК для промышленных конфигураций и расширений, если доступна платформа 8.3.22 или выше. АПК выполняет статический анализ технического качества конфигураций и расширений без запуска и может использоваться для регулярной проверки и CI.

Локальный BSL-сканер из skill не заменяет платформенную проверку, АПК, EDT или проверки команды. Не запускай его автоматически после редактирования; применяй только по явному запросу на проверку.

### EDT и Git

- Для EDT-проекта проверяй ошибки модели, модулей, запросов, прав и структуры проекта.
- Для Git фиксируй атомарность изменений: код, метаданные, формы, роли и миграции должны попадать в согласованном виде.
- Не смешивай в одном изменении рефакторинг, исправление бизнес-ошибки и миграцию формы без необходимости.

### Регрессионные сценарии

- Документы: запись, проведение, отмена проведения, перепроведение, закрытый период.
- Формы: открытие, права, пустые данные, web/тонкий/толстый клиент.
- Запросы и отчеты: пустой период, большой период, дубли, итоги, RLS.
- Интеграции: успех, повтор, таймаут, ошибка контрагента, частичная загрузка.
- Расширения: обновление поставщика, конфликт заимствований, пользователь без полных прав.

## Релизный минимум

Для промышленной доработки предложи минимум:

1. Проверка на копии или тестовой базе.
2. Платформенная проверка конфигурации.
3. АПК или EDT/BSL-проверки, если доступны в команде.
4. Регрессионные сценарии по затронутым бизнес-процессам.
5. Проверка прав пользователя без полных прав.
6. План отката или восстановления.
7. Проверка после обновления, если изменение выполнено через расширение или типовую конфигурацию.

## Формат ответа по тестам

1. Риск изменения и что может сломаться.
2. Какие проверки обязательны, какие желательны.
3. Какой набор тестовых данных нужен.
4. Какие инструменты применить: платформа, АПК, EDT, BSL-проверки, автотесты.
5. Критерий готовности и блокеры релиза.

Для официальных материалов по проверкам используй раздел «Качество» в `references/source-policy-1c.md`.
